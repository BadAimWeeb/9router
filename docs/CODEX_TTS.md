# Experimental Codex speech

Use `cx/speech` with a Codex OAuth connection and `/v1/audio/speech`. Set `response_format` to `mp3`, `wav`, or `json` (base64 MP3); supported voices are arbor, breeze, cove, ember, juniper, maple, sol, spruce and vale (default cove). `ffmpeg` must be installed. The encoded input plus the instruction prefix is limited to 500 UTF-8 bytes; language and style are not supported.

This uses an experimental ChatGPT realtime conversation, not a deterministic TTS API. It can paraphrase, omit or add words; do not use it for safety-critical or verbatim output. Audio is collected with a bounded quiet-tail heuristic and may be truncated. Realtime media travels directly over WebRTC; configured account proxies are rejected rather than bypassed. Availability, protocol and subscription usage may change.

## Experimental client-facing realtime

The custom HTTP protocol below also backs a limited WebSocket adapter described later. Send `POST /v1/codex-voice` with an active API key in `Authorization: Bearer …` or `x-api-key`; a restricted key must allow `cx/gpt-live-1-codex`. Authentication is mandatory even when ordinary API key enforcement is disabled. The response is an NDJSON stream: the first line is `{"type":"session","id":"…"}`; subsequent lines contain either `{"type":"audio","sequence":…, "timestamp":…, "payload":"<base64 Opus>"}` or `{"type":"event","event":{…}}`. Keep the stream open, consume it promptly, and protect the session ID. Events may contain conversation data.

Send each raw 20 ms Opus packet (maximum 4096 bytes) as `POST /v1/codex-voice?session=<id>&action=audio` with the same key. Use `action=cancel` to cancel the current response, or `DELETE /v1/codex-voice?session=<id>` to close. Input is limited to 50 packets per second with a 50-packet burst; payload duration is checked but Opus is not fully decoded. Disconnecting the output stream closes the session. Key revocation or access changes are checked on each operation and approximately every five seconds during streaming.

For PCM, create the session with `POST /v1/codex-voice?format=pcm16`. The session event declares `format`, `sample_rate: 24000` and `channels: 1`; audio events contain base64 raw signed 16-bit little-endian mono PCM in `payload`, without RTP sequence or timestamp. Upload raw PCM using the same audio action: each request must contain 2–3840 bytes and end on a sample boundary. Input is limited to 48000 bytes per second with a one-second burst. FFmpeg with `libopus` is required; codec buffering adds latency. RTP loss or reordering closes PCM sessions rather than concealing gaps; there is no jitter buffer. Cancellation closes both codec processes when the session is closed (response cancellation alone leaves the session open).

One refreshed Codex account is pinned for the session; account and environment proxies are rejected because WebRTC media cannot use them. Media is direct. Sessions are limited to two per process and 90 seconds; slow consumers are disconnected. Use HTTPS, a persistent Node server, a reverse proxy configured for unbuffered streaming, and sticky routing for multiple processes. Serverless deployments are not supported. Usage accounting for these sessions is not available; upstream subscription usage may still apply.

### WebSocket subset

With `custom-server.js`, connect to `/v1/codex-voice/ws?model=cx%2Fgpt-live-1-codex` using an API key in `Authorization` or `x-api-key`. Browser `Origin` requests are rejected; use TLS and a header-capable client. The adapter accepts only JSON `input_audio_buffer.append` (base64 PCM16, 24 kHz mono, 2–3840 bytes per message) and `response.cancel`. Wait for upstream events before sending audio; at most 50 messages may wait for upload. Unsupported or malformed messages close the connection. Upstream events pass through unchanged; decoded audio is emitted as the **nonstandard** `{"type":"9router.audio.delta","audio":"<base64 PCM>"}` because RTP audio has no corresponding response or item identifiers. No session lifecycle, audio completion, input commit, response creation, or other events are synthesized. This is not OpenAI Realtime compatible. The same session limits, revocation checks, proxy restrictions and FFmpeg requirement apply. Use a WebSocket-capable reverse proxy and sticky routing; plain `next start`/`next dev` do not provide this adapter.

### Virtualized OpenAI-shaped subset

`/v1/realtime?model=cx%2Fgpt-live-1-codex` uses the same authentication, limits, transport and deployment requirements. It accepts only `input_audio_buffer.append` and `response.cancel`, optionally with a string `event_id`; unsupported or invalid JSON events return an `error` referencing the client event ID when available. Binary messages and limit violations disconnect. Audio is PCM16 mono at 24 kHz; input is streamed immediately, not committed.

The adapter generates local session, event, response and item IDs and emits GA-shaped `session.created`, `response.created`, `response.output_item.added`, `response.content_part.added`, `response.output_audio.delta`, and `response.done` events. This is an approximation, not full OpenAI Realtime compatibility: session configuration, text, transcription, tools, input commit and response creation are unsupported. Upstream control events are not forwarded. RTP audio has no reliable response boundary: a response starts on the first audio chunk, and an upstream `response.done` ends it with `incomplete` status, never `completed`; late audio may be assigned to a new response, and a response without audio produces no response events. No audio-done event is claimed. A disconnect can end a response without `response.done`.

The terminal item uses `output_audio`, omits raw audio and does not invent a transcript; its incomplete status has no reason because the cause is not an OpenAI-defined reason. This intentionally differs from the [OpenAI Realtime reference](https://developers.openai.com/api/reference/resources/realtime), which describes audio transcripts for normal audio output.

## Official OpenAI Realtime WebSocket proxy

The custom server also exposes the unmodified OpenAI Realtime protocol at `wss://<router-host>/v1/realtime?model=gpt-realtime-2`. See [OpenAI Realtime](OPENAI_REALTIME.md) for supported models and limitations.

Authenticate with `Authorization: Bearer <9router-api-key>` or `x-api-key`. The router validates the local key, applies restricted-key permission to the resolved `openai/<model>` target, selects one active OpenAI API-key account, and sends that account key only upstream. Client frames and OpenAI response frames are relayed without parsing or rewriting, including binary frames; credentials and authorization headers are not logged or forwarded from the client.

This path is bounded to eight sessions per process, ten minutes per session, 1 MiB messages, 1 MiB destination backpressure, and a 15-second upstream setup deadline. Browser `Origin` headers are rejected. The upstream URL is fixed to `wss://api.openai.com/v1/realtime`, and configured account proxies, relay URLs, strict proxy policies, or proxy environment variables fail closed with `503` rather than being bypassed. Use `custom-server.js`; plain `next start`, `next dev`, and serverless deployments do not install this upgrade hook. Multiple persistent processes require sticky routing.

Offline coverage is in `tests/unit/openai-realtime-websocket-check.mjs` and uses a fake upstream without live credentials. This adds transport proxying only: no browser-origin authentication, proxy-pool transport, REST fallback, or post-connect account failover.
